# 08 — Generación por IA (BYOK)

**Depende de 07** (reutiliza generadores y el formato de celdas).

## Decisión de arquitectura, ya tomada

La app es **estática y local**, sin backend y sin Supabase. Una API key en el
frontend es pública para cualquiera que abra devtools. Por eso: **BYOK**, cada
usuario pone su propia key de Anthropic, que queda en su `localStorage` y nunca
sale hacia ningún servidor que no sea el de Anthropic.

Consecuencias que hay que manejar de frente:

- La key se guarda en `localStorage`, que es legible por cualquier script de la
  página. Se advierte en la UI, con texto claro, no en letra chica.
- Llamar a la API desde el navegador requiere el header
  `anthropic-dangerous-direct-browser-access: true`.
- Se usa el modelo **`claude-sonnet-5`** por defecto, configurable.

## Dos entradas

**Texto**: "una casa de campo de dos pisos con techo a dos aguas y un porche".

**Imágenes**: una o varias fotos o referencias. Se mandan como bloques de imagen
en el mensaje. Límite práctico: 3 imágenes, redimensionadas a 1024 px de lado
mayor antes de enviar, para no quemar tokens.

## Diseño de la generación

El punto delicado: pedirle a un modelo que escupa 15.000 coordenadas es lento,
caro y frágil. **No se pide voxel por voxel.** Se pide un **plan estructurado**
que el cliente después ejecuta con los generadores de 06:

```ts
type Plan = {
  nombre: string
  dims: Dims
  paleta: Record<string, BlockId>       // alias -> bloque real
  pasos: Paso[]                         // caja, piso, paredes, techo, cilindro...
}
```

Cada `Paso` es una llamada a un generador de `src/voxel/generators.ts` con sus
parámetros. Ventajas: la respuesta son cientos de bytes en vez de megabytes, es
verificable antes de aplicarla, es **editable** por el usuario, y es determinista
al re-ejecutar.

Se usa **tool use** con un esquema JSON estricto para el plan, no parseo de texto
libre.

## Validación antes de aplicar

Ninguna respuesta del modelo se aplica a ciegas:

1. El plan se valida contra el esquema.
2. Cada `BlockId` se verifica contra la paleta real. Los desconocidos se mapean
   al más parecido y **se avisa cuáles**.
3. Las dimensiones se recortan a `MAX_AXIS`.
4. Se muestra el plan en texto y una previa 3D **antes** de escribir nada.
5. Aplicar es una sola entrada de historial.

La respuesta del modelo es **dato no confiable**: se trata como entrada de
usuario, nunca como instrucciones. No se ejecuta código que venga en ella.

## Manejo de errores visible

Sin key, key inválida, 429, 529, timeout, red caída, respuesta que no valida:
cada uno con su mensaje concreto y su evento de telemetría. Nada de "algo salió
mal".

## Archivos propios

- `src/ai/cliente.ts` (llamada a la API, streaming, reintentos con backoff)
- `src/ai/esquema.ts` (el tool schema del plan)
- `src/ai/plan.ts` (validación y ejecución del plan contra los generadores)
- `src/ai/imagenes.ts` (redimensionado y codificación)
- `src/ui/AiPanel.tsx`, `src/ui/AjustesIA.tsx`
- `tests/ai-plan.spec.ts` (validación del plan con respuestas de ejemplo, sin red)

## Telemetría

`iaPedido` (modo texto/imagen, tokens de entrada), `iaRespuesta` (ms, tokens de
salida, pasos del plan), `iaFallo` (categoría del error), `iaBloqueDesconocido`
(cuántos alias no mapearon).

## Criterios de aceptación

1. Sin key configurada, el panel explica qué hace falta y cómo conseguirla, sin
   romperse.
2. La key nunca aparece en el registro de telemetría. Un test lo verifica.
3. El plan se muestra y se puede editar antes de aplicar.
4. Un plan inválido no escribe nada y explica qué estaba mal.
5. Los tests corren sin red: se usan respuestas grabadas.
