# Tooltips y ayuda contextual — plan de implementación

Workstream 03. Diseño: `docs/superpowers/specs/2026-09-06-tooltips-design.md`.

## Global Constraints

- Código e identificadores en **inglés**. Texto visible y campos del catálogo en
  **español** (es la convención que el repo ya usa en `AXES.help`).
- Comentarios de **20 palabras o menos**, sólo donde explican un porqué.
- Sin punto y coma, comillas simples, encabezados `/* ── nombre ── */`.
- `ayuda.ts` **no importa React**. Es un módulo de datos.
- Después de cada task: `npx tsc --noEmit` sin errores.
- Para correr la suite hace falta build previo y el Chromium del contenedor:
  ```
  npx vite build
  CHROMIUM_PATH=/opt/pw-browsers/chromium-1194/chrome-linux/chrome npx playwright test
  ```
  Sin `vite build`, el `webServer` (que es `vite preview`) espera 120 s y falla.
  Sin `CHROMIUM_PATH`, Playwright busca un binario que no está y fallan los
  tests de navegador por eso, no por código.
- **Este workstream se mergea antes que 04.** No van en paralelo: 04 tipa su
  `helpId` como `HelpId`, y eso no compila sin el catálogo. Que fueran en
  paralelo es lo que hizo fallar el intento anterior.

## Task 3: `Tip.tsx` — mouse y teclado

El componente envuelve un único hijo y le agrega los handlers. No clona el
hijo: lo envuelve en un `<span class="tip-anchor">` con `display: contents`,
que no altera el layout y evita el `cloneElement` con props que el hijo puede
ya tener.

```ts
type TipProps = {
  id: HelpId
  /** Texto dinámico extra, para los ~60 botones de bloque. */
  extra?: string
  children: React.ReactNode
}
```

Apertura y cierre de la tabla del diseño 4.1, en esta task sólo mouse y teclado:

- `pointerenter` con `pointerType === 'mouse'` arranca un timer de 350 ms.
- `pointerleave` con `pointerType === 'mouse'` cancela el timer y cierra.
- `focus` abre **sin demora**: llegar por Tab ya es deliberado.
- `blur` cierra.
- `Escape` cierra sin consumir el evento (el editor también lo usa).

El estado es un `useState<boolean>` más un `useRef` para el timer. El timer se
limpia en el `useEffect` de desmontaje, o queda un `setState` sobre un
componente desmontado.

**Verificación**: `npx tsc --noEmit`. Test manual con `npm run dev` todavía no,
porque no está cableado: se prueba en la Task 7.

## Task 4: `Tip.tsx` — touch

Las dos restricciones del diseño 4.1, que son las que hacen difícil esta task:

**1. Al soltar el dedo se dispara `pointerleave`.** El puntero táctil deja de
existir, y el navegador manda un `leave` que no corresponde a que el usuario se
haya ido a ningún lado. Si el handler de `pointerleave` no filtra por
`pointerType`, la ayuda se cierra en el mismo gesto que la abrió.

```ts
const onLeave = (e: React.PointerEvent) => {
  if (e.pointerType !== 'mouse') return   // en touch el leave es el dedo soltando
  clearTimer()
  setOpen(false)
}
```

**2. En touch no hay `leave` al alejarse**, porque no hay puntero. Sin esto la
ayuda queda abierta para siempre:

```ts
useEffect(() => {
  if (!open) return
  const close = (e: PointerEvent) => {
    if (!anchorRef.current?.contains(e.target as Node)) setOpen(false)
  }
  document.addEventListener('pointerdown', close, true)
  return () => document.removeEventListener('pointerdown', close, true)
}, [open])
```

**3. El long-press no puede disparar la acción del botón.** Es el criterio 3 del
spec. Al cumplirse los 500 ms se marca un ref, y el `click` siguiente se cancela:

```ts
const suppress = useRef(false)
// al abrir por long-press: suppress.current = true
const onClickCapture = (e: React.MouseEvent) => {
  if (!suppress.current) return
  suppress.current = false
  e.preventDefault()
  e.stopPropagation()
}
```
En fase de captura, para llegar antes que el `onClick` del hijo.

Si hay `navigator.vibrate`, un pulso corto al abrir. Es la única señal de que el
long-press funcionó.

**Verificación**: `npx tsc --noEmit`. El comportamiento se testea en la Task 7,
con `hasTouch: true` en el contexto de Playwright.

## Task 5: `Tip.tsx` — posición, accesibilidad, apagado

**Posición**: se mide con `getBoundingClientRect()` del ancla y del tooltip
después de renderizarlo oculto. Arriba por defecto; si el borde superior queda
en negativo, abajo; si se sale por un costado, se corre horizontalmente hasta
entrar. Se mide contra `window.visualViewport` cuando existe: en touch, con el
teclado abierto, es lo único que refleja lo que se ve.

**Accesibilidad**: el nodo del texto está **siempre en el DOM**, con `hidden`
cuando está cerrado, y el ancla lo referencia con `aria-describedby={tipId}`.
Un tooltip que se monta al abrir no lo alcanza el lector de pantalla en el
momento del foco. Se usa `el.hidden`, no `style.display`.

`role="tooltip"` en el nodo.

**Apagado**: `localStorage.getItem('mcb.tips') !== 'off'`, leído una vez en un
`useState` inicializador perezoso. Envolver el acceso en `try/catch`: en modo
privado y con cookies bloqueadas, `localStorage` tira. Si está apagado, el
componente devuelve `children` y nada más, sin listeners ni nodo extra.

**Verificación**: `npx tsc --noEmit`.

## Task 7: Tests de navegador

Necesitan el componente montado, y el cableado todavía no está. Se montan
contra una página de prueba propia, no contra la app: un archivo en `tests/`
que renderiza tres `<Tip>` sobre botones de mentira. Así se testea el
componente sin depender del parche.

1. Hover de 350 ms abre; antes de 350 ms no.
2. Tab hasta el control abre sin demora.
3. `aria-describedby` apunta a un nodo con el texto de `que`.
4. Con `hasTouch: true`: long-press 500 ms abre la ayuda **y el `onClick` del
   botón no corrió**. Es el criterio 3.
5. Con `hasTouch: true`: al soltar el dedo la ayuda **sigue abierta** (la
   restricción 1 de la Task 4), y un tap afuera la cierra (la restricción 2).
6. En las cuatro esquinas del viewport, el tooltip queda dentro.
7. Con `mcb.tips = 'off'` no aparece nada.

Los tests que dependan del cableado real de la app van `test.fixme()` con un
comentario que apunta al doc de integración.

**Verificación**: suite completa verde.

`DesignsPanel.tsx`, `GuideView.tsx`. Es mecánico pero grande, y es donde se
rompe el layout sin querer.

Tres cosas que el cableado obliga a resolver y que la lista de ids no muestra:

1. **Borrar los 13 `title=` existentes.** Si quedan, el navegador muestra su
   tooltip además del nuestro, con otro texto y otro tiempo.
2. **Tres controles con ayuda no son focusables** y necesitan `tabIndex={0}`, o
   la ayuda es inalcanzable por teclado y el criterio 2 no se cumple.
3. **Los ~60 botones de bloque** usan `<Tip id="palette.block" extra={…}>`, con
   el nombre y el id del bloque en `extra`. Es el texto que hoy tienen en su
   `title` y que si no se pierde.

## Notas para quien ejecute

- **El riesgo no es el hueco, es el relleno.** 71 entradas son 71 oportunidades
  de escribir "Hacé click en el botón". Eso pasa el test de cobertura y no
  sirve para nada. Si una entrada no tiene nada útil que decir, el problema es
  el control, no el texto: anotalo en el doc de integración.
- **No crees `src/ui/atajos.ts`.** Es del workstream 04, que va después y que va
  a importar de acá.
- Las Tasks 3, 4 y 5 son el mismo archivo. Están separadas porque el
  comportamiento táctil tiene dos trampas que sólo se ven probando en un
  navegador de verdad, y conviene atacarlas con el resto ya funcionando.
- Si al relevar encontrás un control cuyo comportamiento no entendés leyendo el
  código, probalo con `npm run dev` antes de escribir su texto. Un tooltip que
  describe mal es peor que ninguno.
